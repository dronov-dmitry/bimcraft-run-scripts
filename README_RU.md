# BIMCraft VM Python

[English](README.md) · **Русский**

**BIMCraft VM Python** — плагин для BIMCraft, который выполняет небольшие скрипты
внутри приложения и избавляет от повторяющейся ручной работы.

- Страница установки: <https://dronov-dmitry.github.io/bimcraft-run-scripts/>
- Установка занимает одну команду — см. раздел «Установка» ниже.

Первая часть этого файла — для пользователя, вторая — для того, кто публикует
страницу.

---

# Часть 1. Для пользователя

## Что это даёт

Скрипт делает за вас то, что вы обычно повторяете руками.

- **Меньше ручной работы.** Один запуск вместо десятков одинаковых действий:
  перебрать элементы, отобрать нужные, посчитать, вызвать команды по условию.
- **Сводки и расчёты по вашей модели.** Скрипт собирает данные, считает итоги и
  выводит результат в журнал плагина, где вы его читаете.
- **Одинаковый результат при одинаковых данных.** Сохранённый скрипт можно запускать
  снова и снова — он не зависит от времени, случайности или настроек машины.
- **Безопасно для работы.** Скрипт выполняется внутри BIMCraft в ограниченной среде:
  у него нет доступа к интернету и файлам, ограничены память и время. Ошибка в
  скрипте останавливает только этот запуск и показывает, что и где не так, —
  приложение продолжает работать.

Плагин ставится одной командой, работает сразу после перезапуска BIMCraft и не
требует настройки.

## Как это выглядит на практике

Допустим, вам регулярно нужна сводка по элементам модели: сколько их, какие у них
значения, что изменилось с прошлого раза. Вместо обхода вручную вы запускаете свой
скрипт — он проходит по данным, считает и пишет готовую сводку в журнал. Следующий
раз достаточно повторить запуск.

## Установка

1. Откройте страницу <https://dronov-dmitry.github.io/bimcraft-run-scripts/>.
2. Выберите свою систему — Linux, macOS или Windows — и скопируйте команду.
3. Вставьте её в терминал и нажмите Enter.
4. Подтвердите установку и перезапустите BIMCraft.

**Linux и macOS:**

```bash
curl -fsSL https://bimcraft-plugin-delivery.dronov-dmitry-bim.workers.dev/v1/install.sh | bash
```

**Windows (PowerShell):**

```powershell
iwr -useb https://bimcraft-plugin-delivery.dronov-dmitry-bim.workers.dev/v1/install.ps1 | iex
```

Установщик сам скачает плагин, проверит, что файл скачался целиком и не повреждён, и
положит его в нужную папку. Если плагин уже был установлен, прежняя версия не
удаляется, а откладывается рядом — к ней можно вернуться.

Плагины BIMCraft не подписаны издателем: проверка целостности защищает от битой
загрузки, но не подтверждает автора. Ставьте плагин только со страницы, которой
доверяете, — как и любой другой плагин.

Куда ставится плагин:

| Система | Папка |
|---|---|
| Linux | `~/.config/bimcraft/plugins` |
| macOS | `~/Library/Application Support/BIMCraft/plugins` |
| Windows | `%APPDATA%\BIMCraft\plugins` |

Если вы храните плагины в другом месте, укажите папку в переменной `BIMCRAFT_PLUGINS`
перед запуском команды.

## Как начать пользоваться

После перезапуска откройте **Manage → Plugins**. В списке появится **BIMCraft VM
Python** с двумя действиями:

- **Run Script** — выполнить скрипт;
- **Check Script** — проверить скрипт, ничего не выполняя (полезно перед запуском).

Результат работы — сообщения в журнале плагина, там же видно, на каком месте скрипт
остановился, если что-то пошло не так.

## Обновление и удаление

- **Обновить** — та же команда установки, что и в первый раз. Страница всегда
  предлагает актуальную версию; прежняя сохраняется рядом как резервная копия.
- **Отключить** — в **Manage → Plugins**.
- **Удалить** — удалите папку плагина из папки плагинов (резервные копии можно
  оставить или тоже удалить).

## Если что-то не получилось

- **Плагин не появился в списке** — проверьте, что установка прошла без ошибок и
  BIMCraft перезапущен.
- **Плагин в списке, но помечен как отклонённый** — причина написана рядом и в
  журнале; чаще всего это несовместимая версия BIMCraft.
- **Скрипт остановился с сообщением** — в нём указано, что не так и в каком месте
  скрипта; исправьте и запустите снова. Модель при этом не пострадала.

# Часть 2. Для публикатора страницы

Папка самодостаточна для публикации на **GitHub Pages**: статика без сборки, без
зависимостей и без Node.js. **Это и есть корень git-репозитория для GitHub**:
`scripts/publish-pages.py` инициализирует репозиторий здесь, а не в `delivery/`,
поэтому бэкенд и корневые файлы в GitHub не попадают.

```
frontend/            ← корень git-репозитория; в GitHub уходит только он
  public/            ← артефакт GitHub Pages, публикуется как есть
    index.html
    404.html         GitHub Pages отдаёт его на несуществующие адреса
    styles.css
    app.js           читает манифест у бэкенда, ничего не собирает
    config.js        адрес бэкенда и ссылка на репозиторий; пишет scripts/publish-back.py
    favicon.svg
    robots.txt
    .nojekyll        отключает обработку Jekyll
  tools/preview.mjs  локальный просмотр; в публикацию не входит
  .github/workflows/ pages.yml — единственный workflow репозитория
  README.md          README_RU.md — английский и русский тексты
```

## Как публикуется

`.github/workflows/pages.yml` внутри этой папки на каждый push в `main`,
затрагивающий `public/**`:

1. проверяет, что в `public/` есть обязательные файлы и нет файлов разработки;
2. загружает `public/` артефактом Pages;
3. деплоит.

В настройках репозитория должно стоять **Settings → Pages → Source: GitHub Actions**.
`scripts/publish-pages.py` включает это через `gh api`, если `gh` авторизован.

Адрес проекта: `https://<owner>.github.io/<repo>/`. Все ссылки в странице
**относительные** — иначе на project pages они уйдут в корень домена и получат 404.

Бэкенд (`delivery/backend`) в этом репозитории отсутствует: он деплоится локально
через `scripts/publish-back.sh`.

## Локальный просмотр

```bash
pnpm frontend:dev      # из delivery/, http://127.0.0.1:4173
```

Для проверки против локального бэкенда поставьте в `public/config.js`
`workerBase: "http://127.0.0.1:8787"` и запустите `pnpm backend:dev`.
Страница понимает и `http`, и `https`.

## `config.js`

Единственный файл, который меняется при развёртывании:

```js
window.BIMCRAFT_DELIVERY = {
  workerBase: "https://<worker>.<subdomain>.workers.dev",
  repository: "https://github.com/<owner>/<repo>",
};
```

Его перезаписывает `scripts/publish-back.py` после деплоя бэкенда. Релиз плагина этот файл
не трогает: версии и digest приходят из `/v1/manifest.json`.

## Правила

- Сюда не добавлять: Node-код, сборку, `node_modules`, карты исходников, секреты и
  адреса, которые нельзя публиковать.
- Никаких абсолютных путей (`/styles.css`): сайт живёт в подпапке.
- Данные из сети рендерятся только через `textContent` — `app.js` не собирает HTML
  из ответа бэкенда.
- Скрипты развёртывания живут **вне** этой папки: `../../scripts/`.

## Свой домен

1. Положить `CNAME` в `public/` с одним доменом в первой строке.
2. Настроить DNS у регистратора (для apex — `A`/`AAAA` на адреса GitHub Pages, для
   поддомена — `CNAME` на `<owner>.github.io`).
3. **Settings → Pages → Custom domain**, включить HTTPS.

Файл `CNAME` публикуется вместе с сайтом; без настроенного домена его добавлять нельзя.

## Чек-лист перед публикацией

- [ ] `public/index.html`, `public/404.html`, `public/config.js` не пустые;
- [ ] `config.js` содержит реальный адрес бэкенда, а не `example.workers.dev`;
- [ ] в `public/` нет `.map`, `node_modules`, `.ts`;
- [ ] ссылки относительные;
- [ ] `404.html` открывается и ведёт на `./`;
- [ ] страница в тёмной и светлой теме читается (цвета через `prefers-color-scheme`).
